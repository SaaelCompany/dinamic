# Portal Dynamic Fields — динамические поля на пользовательском портале Jira Service Management

Плагин для Jira Server/Data Center 8.21 + Jira Service Management 4.21, который показывает поля формы
создания запроса на пользовательском портале **только после того, как выбран чекбокс / опция‑триггер**.
Вложенность не ограничена:

```
[x] Медицинский сотрудник
      ├─ [ ] Основная специальность
      │        ├─ Специальность          (выпадающий список)
      │        ├─ Стаж по специальности  (текст)
      │        └─ [ ] Есть сертификаты
      │                 └─ Перечень сертификатов (текст)
      └─ [ ] Дополнительная специальность
               ├─ Специальность (доп.)
               └─ Стаж (доп.)
```

Снятие галки «Медицинский сотрудник» скрывает всё дерево ниже, а значения скрытых полей сбрасываются,
чтобы в запрос не ушли устаревшие ответы.

## Состав

| Что | Где |
|-----|-----|
| Скрипт портала (ES5, без зависимостей) | `src/main/resources/js/portal-dynamic-fields.js` |
| REST `GET/PUT /rest/dynamic-fields/1.0/rules` | `ru.saael.dynamicfields.rest.RulesResource` |
| Хранение и валидация правил (PluginSettings) | `ru.saael.dynamicfields.service.*` |
| Страница администратора `/plugins/servlet/dynamic-fields/admin` | `ru.saael.dynamicfields.servlet.AdminServlet`, `templates/admin.vm` |
| Пример конфигурации | `src/main/resources/example-rules.json` |

## Сборка

Требования: **JDK 8** и **Maven 3.6+** (Atlassian SDK не обязателен — AMPS подключён как обычный Maven‑плагин).

```bash
mvn clean package
# результат: target/portal-dynamic-fields-1.0.0.jar
```

Сборка на JDK 11/17/21 тоже работает: профиль `jdk9-plus` в `pom.xml` включает `--release 8`, поэтому
байткод остаётся версии 52 (Java 8) и Jira 8.21 его загружает. Проверить можно так:

```bash
unzip -p target/portal-dynamic-fields-1.0.0.jar ru/saael/dynamicfields/rest/RulesResource.class | head -c 8 | xxd
# ... 0000 0034  -> major version 52 = Java 8
```

Запуск тестовой Jira c плагином (скачивает Jira 8.21 + JSM 4.21, нужен Atlassian SDK или просто Maven):

```bash
mvn jira:run      # или atlas-run
```

## Установка

1. Administration → Manage apps → Upload app → `target/portal-dynamic-fields-1.0.0.jar`.
2. Administration → Manage apps → **Dynamic fields → Portal dynamic fields** (или `…/plugins/servlet/dynamic-fields/admin`).
3. Вставьте правила (кнопка «Вставить пример» подставит конфигурацию из примера выше), поправьте
   идентификаторы полей, нажмите «Проверить», затем «Сохранить».
4. Все поля, участвующие в правилах, должны быть добавлены в форму типа запроса (Project settings →
   Request types → Edit fields). **Зависимые (скрываемые) поля не должны быть обязательными** — иначе портал
   не даст отправить запрос, пока они скрыты.

## Формат правил

```json
{
  "version": 1,
  "clearOnHide": true,
  "containerSelectors": [],
  "rules": [
    {
      "id": "medical-staff",
      "description": "Чекбокс «Медицинский сотрудник» открывает выбор специальностей",
      "portalId": 1,
      "requestTypeIds": [10, 11],
      "when": { "fieldId": "customfield_10100", "values": ["Медицинский сотрудник"], "negate": false },
      "show": ["customfield_10101"],
      "clearOnHide": true
    }
  ]
}
```

| Поле | Назначение |
|------|-----------|
| `when.fieldId` | id поля‑триггера: `customfield_NNNNN` (виден в URL на странице редактирования пользовательского поля) или системное поле (`priority`, `description`, …). |
| `when.values` | значения, при которых правило срабатывает. Можно указывать **id опций** (`10200`) или **их названия** («Медицинский сотрудник»), регистр не важен. Пустой массив — «поле имеет любое значение» (любая галка стоит, что‑то выбрано, текст введён). |
| `when.negate` | инвертировать условие. |
| `show` | поля, которые видны только пока правило срабатывает. Поле может быть целью нескольких правил — достаточно одного сработавшего. |
| `portalId`, `requestTypeIds` | необязательное ограничение области действия. Оба числа видны в адресе портала `/servicedesk/customer/portal/{portalId}/create/{requestTypeId}`. |
| `clearOnHide` | сбрасывать значение поля при скрытии (глобально и/или для конкретного правила). |
| `containerSelectors` | CSS‑селекторы обёртки поля на форме, если разметка портала кастомизирована. По умолчанию ищутся `[data-field-id]`, `.cv-field-group`, `.sd-field-group`, `.field-group`, `.cv-request-field`, `.form-field`, а при неудаче — ближайший предок, не содержащий других полей. |

Правило «показать» каскадное: поле из `show` видно, только если сработало правило **и видно само поле‑триггер**.
Поэтому для вложенности достаточно сделать поле второго уровня триггером следующего правила — никаких
дополнительных настроек не нужно. Циклические зависимости и ссылки поля на само себя отклоняются при сохранении.

### Варианты «двух новых чекбоксов»

* **Один чекбокс‑поле с двумя опциями** (`customfield_10101` с опциями «Основная специальность» и
  «Дополнительная специальность») — два правила с одинаковым `when.fieldId` и разными `values`, как в примере.
* **Два отдельных чекбокс‑поля** — одно правило с `"show": ["customfield_10101", "customfield_10102"]`,
  а дальше по правилу на каждое поле с пустым `values`.

## Как это работает

* Web‑ресурс с контекстами `customerportal` / `servicedesk.portal.requestcreate` загружает скрипт на каждую
  страницу портала. Скрипт один раз получает правила через REST (эндпоинт доступен анонимно, так как портал
  может быть публичным), а затем пересчитывает видимость при каждом изменении формы (`change`/`input`/`click`)
  и при перерисовке DOM (портал — одностраничное приложение, за ним следит `MutationObserver`).
* Скрытие — класс `sdf-hidden` (`display:none !important`) на обёртке поля; при скрытии чекбоксы снимаются
  программным кликом, списки и текстовые поля очищаются с генерацией событий, чтобы состояние формы совпало с DOM.
* Узнать id полей и опций прямо на форме портала: откройте форму создания запроса, в консоли браузера
  (F12 → Console) выполните `console.table(SaaelDynamicFields.listFields())` — будет таблица
  `fieldId / label / type / options` (для чекбоксов и списков — `id опции = название`). Если объект
  `SaaelDynamicFields` не определён, скрипт плагина на страницу не попал (проверьте, что плагин включён
  целиком, и обновите страницу с очисткой кэша).
* Для отладки: `localStorage.setItem('sdf.debug','true')` (лог в консоли при каждом показе/скрытии), затем
  `SaaelDynamicFields.getConfig()`, `SaaelDynamicFields.readValues('customfield_10100')`,
  `SaaelDynamicFields.containersOf('customfield_10101')`, `SaaelDynamicFields.evaluate()`.

## Ограничения

* Скрытие происходит на стороне браузера; серверная валидация обязательности полей не меняется
  (см. п. 4 раздела «Установка»).
* Если поле‑триггер отсутствует на конкретной форме, зависимые от него поля остаются скрытыми.
* Правила хранятся глобально (PluginSettings); при необходимости область действия ограничивается
  `portalId` / `requestTypeIds`.
